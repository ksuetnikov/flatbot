# GoFlat — обзор проекта

Дата фиксации: 2026-10-26. Описание соответствует коду в репозитории на эту дату. Исходников Go-бота в репозитории нет.

## Назначение

GoFlat — веб-панель учёта недвижимости. Пользователь панели ведёт объекты (квартиры и подобные единицы), счётчики, показания, вложения, доходы и расходы. Арендаторы подключаются к объекту через Telegram-бота: панель выдаёт ключ регистрации, бот пишет состояние этого ключа в общую базу.

Бренд в интерфейсе: `GoFlat`, слоган «Управление недвижимостью» (`resources/js/lib/brand.ts`).

## Основные функции админки

Подтверждено маршрутами `routes/web.php` и страницами `resources/js/pages`.

- Регистрация, вход, сброс пароля, настройки профиля, пароля и темы оформления. Это каркас Laravel React starter kit.
- Список объектов текущего пользователя, создание объекта с именем «Новый объект», удаление объекта.
- Карточка объекта: число подписчиков и счётчиков, статус сдачи показаний за текущий календарный месяц, последнее показание по каждому счётчику, сводка доходов и расходов.
- Настройки объекта: имя, описание, ежемесячное расписание Telegram-напоминаний (день месяца и время), подписчики и счётчики.
- Подписчик: имя (username без `@`), ключ регистрации, признак «уже зарегистрирован в Telegram», username из бота. Ключ можно задать или перегенерировать, пока пользователь не зарегистрирован.
- Счётчик: название и код. История показаний, ручное добавление, правка и удаление. К показанию может быть одно фото. К счётчику можно прикрепить файлы (изображения и PDF) без привязки к показанию.
- Финансы объекта: записи «доход» и «расход» с датой (год, месяц, день), суммой и комментарием. Группировка по месяцам.
- Выгрузка показаний и финансов в XLSX за выбранный или весь период. Внизу файла — итоги доходов, расходов и маржи за тот же период.

Отдельной роли «администратор панели» в таблице `users` нет. Любой зарегистрированный пользователь видит один и тот же интерфейс.

## Ключевые сущности и процессы

| Сущность | Смысл в коде |
| --- | --- |
| `users` / `User` | Учётная запись веб-панели |
| `objects` / `ObjectModel` | Объект недвижимости владельца панели |
| `subscribe_users` / `SubscribeUser` | Подписчик объекта. Поле `name` — Telegram username без `@` |
| `telegram_users` / `TelegramUser` | Слот регистрации бота. Зарегистрирован, если `telegram_id` не `null` |
| `object_properties` / `ObjectProperty` | Счётчик объекта. `value` — последнее показание, синхронизируется из истории |
| `property_readings` / `PropertyReading` | История показаний |
| `object_property_files` / `ObjectPropertyFile` | Файл счётчика или фото конкретного показания |
| `object_finance_entries` / `ObjectFinanceEntry` | Доход или расход |
| `reading_reminder_logs` / `ReadingReminderLog` | Журнал отправленных напоминаний. PHP только удаляет строки при смене расписания |

Основной процесс панели:

1. Пользователь регистрируется и создаёт объект.
2. В настройках добавляет счётчики и подписчиков. На каждого подписчика создаётся строка `telegram_users` с ключом из 8 символов и `state = main_menu`.
3. Подписчик вводит ключ в боте. Бот, по устройству схемы, заполняет `telegram_id` и `username`. Код бота здесь не лежит, этот шаг по записи из бота не проверен.
4. Показания приходят двумя путями: форма панели и `POST /api/meters/` (без аутентификации). После записи последнее значение копируется в `object_properties.value`.
5. Фото показания: `POST /api/meters/{readingId}/photo`. Предыдущее фото этого показания удаляется.
6. Панель показывает, по всем ли счётчикам есть хотя бы одно показание в текущем месяце.

## Пользователи, роли и доступ

- Веб-пользователь: `name`, `email`, `password`. Ролей и разрешений нет.
- Доступ к страницам объектов закрыт middleware `auth` и `verified`. Модель `User` не реализует `MustVerifyEmail`, поэтому middleware `verified` в Laravel пропускает любого вошедшего пользователя. Маршруты подтверждения почты из стартового каркаса при этом существуют.
- Дашборд выбирает объекты через `$user->objects`. Страницы конкретного объекта резолвят `ObjectModel` по id и не сравнивают `user_id` с текущим пользователем. Вызовы `$this->authorize(...)` в контроллерах закомментированы.
- `App\Policies\ObjectModelPolicy` всегда возвращает `false` и ссылается на несуществующий класс `App\Models\ObjectModel` (фактическая модель — `App\Models\Object\ObjectModel`). В `AppServiceProvider` политика не регистрируется.
- `telegram_users.is_admin` — флаг бота, не роль панели. При создании подписчика PHP ставит `false`. Сидер может создать слот с `is_admin = true`. Панель этот флаг не читает.
- `POST /api/meters/` и `POST /api/meters/{readingId}/photo` не имеют middleware аутентификации, сессии и CSRF.

## Взаимодействие с Go-ботом

Исходников бота в репозитории нет. Комментарий в `config/services.php` и команда `app:reset` называют его goBot и общей SQLite.

Подтверждённые каналы:

- Общие таблицы. Панель создаёт слот `telegram_users` и строку `subscribe_users`. Дальнейшее заполнение `telegram_id`, `username`, `first_name`, `state` из PHP не выполняется, кроме начального `state = main_menu`.
- Входящий HTTP приёма показаний и фото. Вызывающая сторона в коде не названа. Контракт описан в `API_AND_INTEGRATIONS.md`.
- Исходящий HTTP `UpdateObjectJob` на `GO_API_OBJECT_POST_URL`. В `config/services.php` этот путь помечен устаревшим: он создавал дубликаты в общей SQLite, и URL не следует задавать при общей базе. Событие `AfterUpdateObjectEvent`, которое ставит эту задачу в очередь, в коде приложения нигде не диспатчится.

Колонки `objects.user_code` и `objects.bot_properties` созданы миграциями с комментариями про Telegram и JSON для бота. PHP их не читает и не пишет. Кто их заполняет — не проверено.

`reading_reminder_logs` описана миграцией как лог отправленных Telegram-напоминаний. Вставок из PHP нет. При изменении `objects.notification_date` все строки журнала этого объекта удаляются.

## Ограничения и особенности

- Мягкое удаление не включено: колонки `deleted_at` есть у `objects`, `object_properties`, `subscribe_users`, трейт `SoftDeletes` не подключён. `delete()` удаляет строку. Связанные строки с `cascadeOnDelete` удаляются базой. Удаление объекта не удаляет связанные `telegram_users` (внешний ключ направлен от `subscribe_users` к `telegram_users` с `nullOnDelete`). Удаление подписчика через сервис отдельно уничтожает его `telegram_users`.
- `order` при создании объекта, счётчика и подписчика всегда записывается как `1`. Интерфейса сортировки нет.
- Уникальность `registration_key` проверяется в PHP, уникального индекса в миграциях нет.
- Расписание напоминаний хранится как «настенные часы» (каст `MonthlyNotificationSchedule`), колонка при этом `timestamp`. Фактическое преобразование часового пояса драйвером БД не проверялось. Часовой пояс приложения по умолчанию — `Europe/Moscow`.
- Очередь и сессии по умолчанию сидят в той же БД (`QUEUE_CONNECTION=database`, `SESSION_DRIVER=database`, `CACHE_STORE=database`).
- Доменные сценарии (объекты, показания, бот, финансы) тестами не покрыты. Тесты есть только у стартового каркаса аутентификации и дашборда.
